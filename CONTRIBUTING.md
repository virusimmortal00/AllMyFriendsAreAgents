# Contributing

Thanks for helping improve All My Friends Are Agents. Contributions may begin
in a room, local experiment, or private conversation, but the repository must
contain the durable context needed to understand and review them.

## Choose the right channel

- Use GitHub Issues for reproducible bugs and scoped, actionable feature work.
- Use pull requests for code or documentation changes with a clear rationale and
  verification record.
- Use `SECURITY.md` for suspected vulnerabilities. Do not disclose vulnerability
  details in a public issue, discussion, or pull request.
- Exploratory conversations can happen elsewhere, but restate their outcomes and
  decisions in the relevant public issue or pull request. Do not make private
  chat history a prerequisite for participation.

## Write for the public record

Assume readers cannot access private rooms, meetings, provider sessions, local
machines, or internal planning notes.

- Explain project-specific terms and link to stable public context.
- State what is verified, what was reported but not reproduced, and what remains
  a hypothesis.
- For bugs, include expected and actual behavior, minimal reproduction steps,
  relevant versions, and only the environment details that affect the result.
- Prefer public URLs, repository paths, commits, tests, and sanitized evidence.
- Replace private names, domains, paths, repositories, and credentials with
  obvious placeholders.
- Do not paste raw prompts, transcripts, model output, private URLs, customer
  data, secrets, or unfiltered logs.

Private agent feedback should normally be paraphrased into a standalone
observation, requirement, or question. Name a model or quote a participant only
when the attribution is relevant, intentionally public, and understandable to a
reader outside the original conversation.

## Agent-assisted contributions

Agents may help draft issues, changes, and reviews. A human must explicitly
authorize external publication and remains responsible for the result. When the
project's governed contribution workflow performs the publication, use its
scoped approval path.

Do not add automatic "generated by" signatures, model attribution, or agent
co-author footers. If model identity is necessary to reproduce provider-specific
behavior, include it as technical environment information instead.

## Pull requests

Before opening a pull request:

1. Explain what changed and why.
2. Link the relevant issue or public design context when available.
3. Run the appropriate checks:

   ```bash
   pnpm run test
   pnpm run build
   ```

4. Include the commands run and any meaningful manual verification.
5. Review the diff for secrets, private context, machine-specific paths, and
   unrelated generated files.

Follow `.github/ISSUE_TEMPLATE/work-item.md` for work-item structure and
`AGENTS.md` for the complete agent publication policy.
